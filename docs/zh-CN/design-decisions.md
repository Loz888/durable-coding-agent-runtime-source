# 设计取舍

[English](../design-decisions.md) | [简体中文](design-decisions.md) | [中文首页](../../README.zh-CN.md)

本文介绍本仓库实现中的技术选择及其代价。

| 选择 | 原因 | 代价与边界 |
| --- | --- | --- |
| PostgreSQL 队列 | 持久化领取与 Run 元数据共享事务中的执行授权校验 | 数据库可用性与行锁竞争会影响调度 |
| FOR UPDATE SKIP LOCKED | Worker 避开已被其他领取者锁定的记录 | 空轮询是合法结果，不保证严格公平 |
| Epoch 隔离校验 | 旧进程可能在接管之后恢复 | 每一次受控写入都必须校验授权代次 |
| Revision CAS | 仅凭持有者身份无法排序并发检查点 | 冲突后需要重新加载并核对预期版本 |
| Git Worktree | 隔离修改，并保留可检查的源码基线 | 依赖可信的本地 Git 元数据与生命周期管理 |
| Patch Intent/Result | 跨越文件系统写入与 SQL 提交之间的窗口 | 必须核对实际哈希，未知内容应停止 |
| 短时受保护事务 | 让补丁写入与领取、续约串行协调 | 较慢的文件操作仍可能延迟续约并导致过期 |
| 模型与测试在行锁之外运行 | 避免在网络与构建期间持有行锁 | 完成后必须重新检查执行权限、绑定与哈希 |
| 分离预算 | 崩溃、重试与新提案消耗不同资源 | 需要更多计数器，但接管无法重置预算 |
| 保留包名 | 保留经过测试的组件边界 | 命名不完全常规，避免大规模重构风险 |

## 外部副作用

诊断路径在执行工具前保存模型与工具意图，再通过后续检查点保存输出。
崩溃后，待完成调用可能重放。
持久化执行顺序不等于对任意外部副作用都保证“恰好一次”。
受控的补丁修改可以根据 Before/After SHA 采用更具体的恢复策略。
